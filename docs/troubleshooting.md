# Troubleshooting by phase

Commands labeled **WSL** run in `/mnt/c/projects/vaultwarden/ansible`; **VM** means a trusted SSH session or Proxmox VM console; **CMD** means native Windows CMD. Set `KEY_NAME=vault_01_ed25519`, `VM_HOST` and `VM_USER` in WSL to your chosen key and actual OpenTofu IP/user outputs before using those variables. Use diagnostics locally; don't publish secret-bearing logs.

| Symptom | Likely cause | Diagnostic command and shell | Fix |
| --- | --- | --- | --- |
| `wsl` opens in the wrong directory | Shell startup or different checkout location | WSL: `pwd; ls -la` | `cd /mnt/c/projects/vaultwarden/ansible`; use the actual mounted checkout path. |
| Windows profile path or username is wrong | Windows and WSL homes/users differ | CMD: `echo %USERPROFILE%`; WSL: `whoami; echo "$HOME"` | Resolve `WIN_HOME` using `cmd.exe`, `wslpath` and `tr` as in Phase D; do not assume matching usernames. |
| Private key missing from WSL | Key only exists on Windows or filename differs | WSL: `ls -l "$HOME/.ssh/$KEY_NAME"` | Copy the matching Windows key with `install -m 600` per Phase D. |
| `UNPROTECTED PRIVATE KEY FILE` | Key loaded from Windows mount or excessive modes | WSL: `ls -ld ~/.ssh; ls -l ~/.ssh/vault_01_ed25519` | Use Linux-home copy, `chmod 700 ~/.ssh` and `chmod 600 ~/.ssh/vault_01_ed25519`. |
| No agent / repeated passphrase / wrong identity | New Linux session or incorrect agent key | WSL: `ssh-add -l` | Start agent if necessary; `ssh-add "$HOME/.ssh/$KEY_NAME"`; use `-o IdentitiesOnly=yes -i` for direct SSH. |
| `Permission denied (publickey)` | Public/private key mismatch or unauthorized key | WSL: `ssh -v -o IdentitiesOnly=yes -i "$HOME/.ssh/$KEY_NAME" "$VM_USER@$VM_HOST"` | Compare client public-key fingerprints; verify guest `authorized_keys` via console. Do not replace keys blindly. |
| Correct key but wrong guest login | Inventory differs from cloud-init username | CMD in `opentofu`: `tofu output -raw vm_username`; VM console: `getent passwd debian` | Set `VM_USER` and `ansible_user` to the configured existing account. OS name alone does not choose the username. |
| Unknown or changed host fingerprint | New VM, reinstall, changed IP or an unexpected server | VM console: `sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` | Verify trusted fingerprint. For a confirmed rebuild only, WSL: `ssh-keygen -R "$VM_HOST"`, then reconnect and compare. Never disable host-key checking. |
| SSH times out / VM unreachable | Wrong IP, route, bridge, firewall or service | WSL: `ip route get "$VM_HOST"`; VM console: `ip -br address; ip route; sudo systemctl status ssh --no-pager` | Verify static CIDR/gateway/bridge; permit intended TCP 22 traffic; finish cloud-init. A failed ICMP ping alone does not establish SSH failure. |
| DNS lookup fails | Resolver not reachable or inherited DNS unsuitable | WSL/VM: `getent hosts download.docker.com` | Correct DNS/resolver routing; set guest `dns_servers` and review OpenTofu plan. If using an SSH hostname, test that exact hostname too. |
| `no hosts matched` / unable to parse inventory | Wrong filename, missing file, invalid YAML or wrong group | WSL: `ansible-inventory -i inventory/hosts.yml --graph` | Create/edit `hosts.yml` from `hosts.example.yml`; ensure group `vault` exists. This project has no `hosts.ini`. |
| `config file = None` under `/mnt/c` | Ansible skipped world-writable-directory discovery | WSL: `ansible --version` | Select reviewed config with `export ANSIBLE_CONFIG="$PWD/ansible.cfg"`; establish checkout trust or move the reviewed Ansible working copy to native WSL storage. |
| Role not found | Wrong config/working directory | WSL: `ansible-config dump --only-changed` | Run inside `ansible/` with its config; `roles_path = roles` must resolve to that checkout's roles. |
| Compose module not found | Collection not installed in this Linux environment | WSL: `ansible-galaxy collection list community.docker` | `ansible-galaxy collection install -r requirements.yml`; Windows installation does not install Linux collections. |
| Remote Python missing | Incomplete template | VM console: `python3 --version` | Install `python3` and `python3-apt` on the guest and fix the template before new clones; rerun SSH/ping checks. |
| Missing sudo password / user not in sudoers | Privilege setup differs from cloud-init expectation | VM: `sudo -v` | Use `--ask-become-pass` with guest sudo password, or correct that user's sudo policy via console. |
| Cloud-init wait fails | Template errors, stale state or unreachable services | VM: `sudo cloud-init status --long; sudo journalctl -u cloud-final --no-pager` | Fix the reported template/configuration issue, then retry; do not blindly rerun destructive cloud-init cleanup on a running vault. |
| Proxmox API 403 | Token/user ACLs insufficient | PROXMOX WEB INTERFACE: token privileges, user ACLs and task log | Grant only the privileges required for target cloning/storage/VM operations; check privilege separation. |
| API TLS error | Untrusted Proxmox CA or hostname mismatch | CMD: confirm `proxmox_endpoint` in private tfvars | Trust the correct CA/hostname in Windows. `proxmox_insecure=true` is an explicit API-TLS exception, not an SSH workaround. |
| App role requires `.env` | Remote private config not created | VM: `sudo test -f /opt/vaultwarden/.env` | Complete Phase F's remote file creation with actual HTTPS DOMAIN, then rerun `site.yml`. |
| Container does not start / unhealthy | Bad env, image pull, disk capacity or application error | VM root in `/opt/vaultwarden`: `docker compose config --quiet; docker compose ps; docker compose logs --tail=100; df -h` | Correct the reported error, restore capacity or valid settings, then rerun; never delete SQLite WAL files as a shortcut. |
| Local health works but public 502 | Wrong connector location/origin | VM: `curl -fsS http://127.0.0.1:8080/alive; sudo systemctl status cloudflared --no-pager` | Run connector on the same VM and route to HTTP loopback port 8080; see tunnel guide. |
| Browser works but clients fail | Wrong external URL or interactive Access challenge | Check client self-hosted URL and Cloudflare policy | Use the exact HTTPS DOMAIN; review Access/proxy/WebSocket behavior, then retest sync. |

Resume the failed phase of [onboarding](windows-wsl-ansible.md) only after its check passes. For maintenance and recovery, see [operations](operations.md) and [backup/restore](backup-restore.md).
